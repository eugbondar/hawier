# EXTENSIONS — the hawier extension mechanism

> **What is here and what is in the specs.** The mechanism's contract — which
> slots exist, what crosses the boundary, what a node does without a module,
> deadlines, the sandbox, parameters and their API — lives in the specs
> [`extension-host`](openspec/specs/extension-host/spec.md) and
> [`first-party-extensions`](openspec/specs/first-party-extensions/spec.md);
> the contracts of individual points are in
> [`artifact-delivery`](openspec/specs/artifact-delivery/spec.md),
> [`event-delivery`](openspec/specs/event-delivery/spec.md),
> [`artifact-retention`](openspec/specs/artifact-retention/spec.md),
> [`rollout-engine`](openspec/specs/rollout-engine/spec.md),
> [`access-control`](openspec/specs/access-control/spec.md). This file is
> **why** the mechanism is built this way, its narrow places, and what is not
> done yet.
>
> **Status (2026-10-26): seven points in the ABI, eight modules, six tasks out
> of eight closed.** Done: storage (§4.6), events (§4.1), retention (§4.2),
> rollout (§4.7/4.8), console tabs (§4.5) and **permissions** — half of §4.4.
> There is not a single in-core implementation.
>
> **Not done:** the second half of §4.4 — `AuthProvider`, i.e. OIDC: there is
> no code at all, login is Basic against config users only, and
> `hawier_session.secret` still stores the password (SCHEMA_NOTES #18). §4.3
> remote-shell as a whole: no tables, no `_link`, no branch in the client, no
> `TARGET_REMOTE_SHELL` permission. Action events (`ActionFinished/Errored`)
> and emission from the DDI path (§4.1).
>
> **Known gaps of the mechanism itself:**
> - an extension cannot serve data (there is no point that answers HTTP), so a
>   declared tab must point at an existing mgmt endpoint, and an extension
>   cannot have an entity of its own;
> - the manifest's limits and sites (`deadline_ms`, mem, fuel, `sites`) are
>   **only displayed**, not enforced: there is a single deadline for all —
>   `HAWIER_EXT_DEADLINE_MS`, memory is the host's fixed 64 MiB, there is no
>   "approval" of capabilities — the `http_out` hosts are taken from the
>   module's manifest as is (§3);
> - a module failure is distinguished by kind: a transport failure (trap,
>   deadline, broken frame) is `503` with `Retry-After`, while an `err` from
>   the module or an unreadable response is `500`; a failed `rollout.evaluate`
>   leaves the rollout RUNNING instead of pausing it (§2);
> - the `hardened` profile is run by `make e2e` (a node without classic
>   rollout, the bucket strategy, `target.type.required=true`) against
>   SWUpdate/suricatta in QEMU; the remaining items of API_NOTES §6, except
>   item 6, are still not implemented;
> - parameters are handed to guests as one flat map (NARROW in §5); a module's
>   manifest can depend on a parameter, so the declared capabilities are a
>   function of the configuration read at startup.
>
> Divergences of the code from the intent, found during the move to OpenSpec,
> are listed in the design.md of the change `baseline-existing-capabilities`
> (catalog, items 7–9, 12–13, 21).

The mechanism was designed for eight concrete tasks, and all eight must be
expressible in one way, not eight:

1. webhook events (the appearance of release rollouts and so on);
2. auto-rules (cron) for deletion — for example, of non-release dev artifacts;
3. remote-shell to a device over HTTP (in the long run — a device console
   over long-poll);
4. oauth and permissions;
5. custom view tabs in the console tree;
6. s3;
7. custom rollout logic;
8. the classic ("default") rollout logic — as an extension that the hardened
   build does not take.

## 1. Extension points and transports

An **extension point** is a typed contract (serde DTOs in
`libs/api/src/ext.rs`). The implementation is a **wasm module** that the host
loads and calls. There is no other transport.

Why wasm and not a separate process: a wasm module has no ambient authority at
all — no file system, no sockets, no processes, nothing except what the host
hands it as imports. A native program has the same authority as the user it
runs as, and the rule "an extension does no I/O" remains an agreement, not a
fact. The second argument: a module is a single architecture-independent file;
it can be carried around, swapped, and distributed as data.

What the host hands the guest is deliberately little: a WASI context without
directories, sockets, and stdin/stdout (stderr is inherited — for
diagnostics), environment variables with the `HAWIER_EXT_` prefix minus the
reserved ones, and one host import — an HTTP call, which refuses until the
module has declared `http_out`. No base URL, no internal token — an extension
will not read the node's secrets even by accident.

The guest ABI is four exports generated by the macro
`hawier_api::wasm_extension!`; inside it is the same JSON as everywhere here:
the contract does not change with the transport.

First-party extensions are ordinary modules in this same monorepo, all eight
`apps/ext-*`. The integration tests load exactly them, not stubs, so the
transport is exercised by the whole test suite, not by one dedicated test.
They are built with `make ext`.

## 2. The only hard ABI invariant

> **Artifact bytes do not cross the extension boundary, and neither do handles.**

The wording was refined (2026-09-06). It used to say "an extension does not go
to the network", which was broader than needed: a request for information
needed to make a decision is not the same as hauling a payload. Because these
two things were conflated, OIDC had to be bent into "the host fetches the JWKS
itself", and the `http_out` authority declared in the ABI would have stayed
unimplemented for years.

There is no such thing as an extension point that "has to be native". There
are **host duties that are not extension points**: moving bytes, DB
transactions and locks, the rollout engine's state machine, issuing secrets.
If a scenario needs bytes, the extension returns a URL or a descriptor, and
the host moves the bytes.

The canonical example is s3 (§4.6): the extension returns a tokenized link to
the file, and that is all; it does not enter the byte path at all, so it
requires no "nativeness".

Consequences:

- an extension never holds a `PgConnection` and is never inside
  `FOR UPDATE SKIP LOCKED`: the host loads a snapshot → calls the extension
  with a deadline → applies the decision in its own transaction;
- an extension has no ambient I/O — only the **capabilities** declared in the
  manifest. `http_out` has a one-megabyte body ceiling as part of the
  invariant: without it the authority would become a way to smuggle an
  artifact through. Many points need no capabilities at all: they are pure
  functions;
- a guest call is synchronous, so the calling thread waits for the answer.
  This is the price of `http_out`, and it is why the descriptor model remains
  the default wherever the extension does not need to ask anything;
- **intended:** a timeout, panic, or invalid response → a declared safe
  default (dead-letter, rollout pause, access denied), not a failed request or
  engine. **Currently** this holds for transport failures (they become
  "service unavailable", i.e. `503` on the request path), but not for a
  module's `err` (`500`) nor for rollout (the rollout stays RUNNING) — see the
  status at the top.

## 3. Execution site

Each point declares an execution site — this is more honest than the blanket
"guests only on the control node":

- **`control`** — the control node's background loop (`spawn_background` in
  `apps/server/src/lib.rs`). Retention, the event drainer, rollout
  strategies.
- **`request`** — the mgmt/UI request path, a tight deadline and a cache.
  Permissions.
- **`ddi`** — the device path, **including sub-nodes**. Storage, the future
  shell policy. A sub-node must execute `ddi` extensions while the control
  node is dead: this is a direct consequence of the "DDI does not depend on
  singletons" invariant (spec `node-roles`).

The **manifest** names the points, capabilities, limits, and sites. **Currently
the host enforces only the points** (a module that did not declare a point of
its slot is not loaded) and `http_out` (exact host match). Sites and limits
are merely shown in `/rest/v1/system/extensions`; nothing prevents loading a
`control` module on a sub-node. **Plan:** check the site at load time, apply
the manifest limits as an upper bound under the common deadline, cache the
results of `ddi` points (presign cache), and grant only operator-approved
capabilities rather than whatever the module itself declares.

The **ABI** is serde DTOs in `libs/api` (we do not create new shared libs,
CLAUDE.md). The host is a module in `apps/server`. A guest SDK for plugin
authors is an external crate in the future, not part of the monorepo.

### 4.6. Storage — the extension returns a descriptor ✅

The contract is [`artifact-delivery`](openspec/specs/artifact-delivery/spec.md)
and [`first-party-extensions`](openspec/specs/first-party-extensions/spec.md).

Why the "where" decision can be moved out without moving anything else:
everything essential about a download was and remains the host's — device
authentication, the check that the module is assigned to it, `.MD5SUM`,
conditional headers by sha1, Range, and writing the `DOWNLOAD` status. The
extension adds only the "where". If it is a URL with an allowed redirect, the
host answers 302 — the bytes do not go through hawier at all, which is exactly
what s3 is for — and `DOWNLOAD` is still written, because the request arrives
here. On upload the spool stays in the core: it is the byte path, and the
content-addressed name cannot be known until the end of the stream. Deletion
happens only after checking that nobody else references the sha1: the
extension does not know about the database and must not. SigV4 lives inside
`ext-s3` (HMAC from `hawier_api::ext`) — we do not pull in an SDK or
`object_store`.

- **NARROW:** with a 302 the device sees the storage's ETag (for multipart —
  not the sha1), and `If-Match` is not enforced on its side. Integrity does
  not suffer: the client verifies sha1/md5 on the fly. Range works natively
  on S3.
- **NARROW:** a presigned URL is a bypass of hawier's authorization for the
  duration of the TTL. Keep the TTL short, do not log the URL.

### 4.1. webhooks — `EventSink` + transactional outbox ✅ pipeline done

The contract is [`event-delivery`](openspec/specs/event-delivery/spec.md).

Rollout creation also became transactional — before, a half-created rollout
was possible, and now the event shares the fate of what it reports.
Subscriptions are ordinary console resources (the "no custom lists" rule), so
they get sorting, pagination, search, and saved views for free. The mask is
validated against the known kinds: a subscription to a nonexistent kind would
look healthy and stay silent forever. `EventSink` is pure by default: it
returns a descriptor (`POST url, headers, body` + signature), and the host
performs the HTTP; `http_out` is an escape hatch for non-standard
authorization, not the norm.

**Not done:** the `ActionFinished/Errored` events and emission from the
action-status write — only for a fresh row, after the repeat-collapse, so that
device spam does not produce events by itself; on the DDI path — opt-in.
Currently there are seven kinds, and none is emitted from the DDI path.

### 4.2. cron retention — deletion rules ✅

The contract is [`artifact-retention`](openspec/specs/artifact-retention/spec.md).

**Three parties, and none can substitute for another.** The rule narrows the
field (RSQL + minimum age), the extension decides what of that may be deleted,
the host deletes. SQL cannot express "keep the last three", the extension
cannot reach the file, the host has no policy. Hence the protections against a
mistake in the extension: only the ids proposed by the host are honoured, the
blob goes after the last reference, `dry_run` is the default — automation that
deletes first only tells what it would do. Validation on write exists because
a rule that cannot execute is worse than a missing one: it looks armed. The
policy plan is deterministic — otherwise a dry run would not predict the real
run.

**Intended:** a rule does not fire right after creation — the count starts
from the moment of creation, not "the cron already passed sometime in the
past". **Currently** a rule created via the API does not fire at all: a
never-run rule is measured from "now" on every tick, and `created_at` is not
read (catalog, item 7). Also there: the rule's claim is released before the
work itself.

**A departure from the original plan.** We did not generalize `housekeeping`
into a job registry: each rule has its own cron in the table, and the tick
simply asks which are due. A registry for two hardcoded jobs plus one
table-driven one is ceremony without benefit.

- **NARROW:** a rule can hit an artifact that a future DS will reference.
  Selection only by age and filter, `dry_run` by default, and an explicit
  `active` — this mitigates but does not eliminate it; it is closed for good
  only by a policy that looks at intent rather than age.

### 4.7 / 4.8. Rollout — `RolloutStrategy` ✅

The contract is [`rollout-engine`](openspec/specs/rollout-engine/spec.md) and
[`first-party-extensions`](openspec/specs/first-party-extensions/spec.md).

The engine kept the mechanics — SCHEDULED actions, rollout claim, group
activation, dynamic growth, completion — and handed out exactly two decisions:
how to split the fleet and when a group is ready. hawkBit's classic percentage
logic is now the module `apps/ext-rollout-classic`; the hardened node simply
does not load it, and then the only rollout logic in the system is the one its
operators chose.

**The extension is not passed a list of targets.** A rollout may cover tens of
millions of devices, so the module receives their *count* and the group
definitions, and returns **selectors** that the host executes in SQL. A side
benefit: the built-in split loaded all matching ids into memory, now it is
only `COUNT(*)` and `INSERT ... SELECT`.

**The call is outside the claim transaction.** The host reads a snapshot
without locking, asks, then claims the rollout and applies the answer after
re-checking the status: a rollout that another node processed in the meantime
is skipped, not applied halfway.

**A strategy cannot drive the engine into an unknown state.** It returns a
verdict on the groups shown to it, while the transitions stay with the host.
Groups the plan did not take are deleted: otherwise the rollout would drag
empty ghost groups along. (That the verdict concerns only the groups of this
rollout the host currently does not check — catalog, item 13.)

The strategy choice is the sidecar `hawier_rollout_ext`; `sp_rollout` is
untouched. A name that no loaded module knows is rejected on create:
otherwise the rollout would hang in CREATING forever, looking merely slow.
**A hole:** only an explicitly sent name is checked — a rollout without
`strategy` on a node with no rollout module (or only `ext-rollout-bucket`)
hangs exactly that way (catalog, item 9).

**The canary strategy** (`apps/ext-rollout-bucket`) is the owner's original
scenario: trial waves over random groups, the next wave on success. The bucket
is computed from controller_id, not reported by the device: no firmware
support needed, identical on all nodes, unchanged on re-registration. This
also sidesteps SCHEMA_NOTES #21 — the attribute would be text, and
`attribute.bucket=le=50000` would compare lexicographically, quietly picking
the wrong devices. The windows are pseudorandom but deterministic from the
rollout id: a canary that cannot be reproduced is not a canary.

### 4.4. oauth and permissions — `AuthProvider` + `Authorizer`

**Permissions are done** — the contract is in
[`access-control`](openspec/specs/access-control/spec.md). They are built
differently from what was planned: instead of a `perms` field on the extractor
and point-wise `require(perm)`, there is one layer over mgmt that classifies
every `(method, path)` into a hawkBit-style permission, and anything
unclassified falls into REPOSITORY permissions, so there is no endpoint left
open by oversight. The decision is made by `ext-authz`; enforcement, the
verdict cache, and roles/grants are the host's. Enforcement starts with the
first grant, not the first role: defining a role does not yet mean switching
checking on.

**Not done — `AuthProvider`**: token → `username + tenant + roles`. Basic
against config users becomes the builtin implementation; OIDC is the second
(JWT validation against issuer/JWKS with a cache). A guest provider is
acceptable in the narrow "claims → roles" role (cacheable). Session issuance
stays the host's; `hawier_session.secret` (replay of the mgmt password,
SCHEMA_NOTES #18) is a reason to move to server-issued tokens together with
OIDC.

### 4.3. remote-shell — host-owned channel, extensible policy (planned)

A real TCP tunnel cannot exist: multi-node, HATEOAS, and long-poll.
**Store-and-forward through Postgres:**

- `hawier_shell_cmd(id, tenant, target, cmd, state, created_by,
  created_at)` and `hawier_shell_chunk(cmd_id, seq, stream, data, at)`;
- the operator queues a command via mgmt/UI → INSERT;
- the device's poll gets a new `_link` `remoteShell` **only when a pending
  command exists** and the tenant toggle is on (link contract — API_NOTES
  §8);
- the device GETs the command, executes it, POSTs the output in chunks to the
  href-derived feedback — strictly per the API_NOTES §2 doctrine (follow
  `_links`, do not build URLs from base);
- any sub-node serves the command, because everything is in the DB;
- client: a branch on the `remoteShell` link in the `hawier-device` loop;
- console: a terminal panel on the target card; the future live console is
  the same channel in small chunks.
- **NARROW:** do not weigh down poll — the pending check goes into the
  existing `LEFT JOIN LATERAL` of controller-base, not into a separate query.
- **Security (the largest blast radius):** this is RCE across the fleet.
  Per-tenant toggle, **off** by default; the `TARGET_REMOTE_SHELL` permission;
  an audit of every command in `hawier_action_log`; the `ShellPolicy` point
  ("is this command allowed") is extensible.

### 4.5. Custom view tabs — `ConsoleSurface` ✅

The contract is [`console-lists`](openspec/specs/console-lists/spec.md),
[`ui-state-api`](openspec/specs/ui-state-api/spec.md),
[`first-party-extensions`](openspec/specs/first-party-extensions/spec.md).

The console registry became data: the built-in is merged with the declared.
The literal table kept its shape — next to it lives a compilable form that is
converted, otherwise sixteen resources and fifty-odd views would have turned
into a thousand `to_string()` calls where the compiler checks nothing.

The console is a separate process without its own extension host, so it reads
the declarations from the node via `/ui/v1/surfaces`, like all other state. If
the node did not answer, the console comes up with the built-in tree: that is
a working console, not a reason not to start.

**A boundary worth naming out loud: an extension does not supply data.** There
is no point that serves HTTP, so a declared node points at an already existing
mgmt endpoint. It is a named query raised to a full place in the navigation,
not a new entity with its own storage. A whole entity will become possible
only when there is a point where an extension answers mgmt requests.

The built-in wins a name conflict: a declaration cannot replace a core
resource by pretending to be it. A discarded view is written to the log —
before, silently, and the only view the shipped extension declared
(`rollouts/needs-attention`) was lost this way the whole time it shipped; it
cannot be an error, because the console must come up with any declaration. (A
discarded *resource* is not yet written to the log — catalog, item 27.)

**Checked on par with the built-in.** The audit walks the merged registry, so
a declared tab must satisfy the same rules — on its very first run this caught
the demo extension that declared a `pollStatus` column which is absent from
the compact response. A separate check confirms that the declarations arrived
at all: without it, all the others would pass even with a silently lost merge.

**What ships as an example.** `apps/ext-console` declares only views: queries
interesting to a particular deployment. It declares no node of its own —
`fleet-health` was removed, because "who is responding" is a product question,
not a deployment one, and it moved into the built-in Targets resource, where
the server computes liveness from the tenant's polling configuration. The
`health` icon is reserved for declared nodes.

## 5. Configuration and profiles

Extensions are not in cargo features: they are separate `.wasm` files, and a
node is configured by which of them it loads. The variables are in the README
("Environment variables (server)"), the rules are in the `extension-host` spec.

An example of a node on file storage and webhooks:

```
HAWIER_EXT_STORAGE=/usr/local/lib/hawier/hawier_ext_fs.wasm
HAWIER_EXT_EVENT_SINK=/usr/local/lib/hawier/hawier_ext_webhook.wasm
HAWIER_EXT_FS_ROOT=/var/lib/hawier/artifacts
HAWIER_ARTIFACT_DIR=/var/lib/hawier/artifacts
```

**A module is loaded at node startup**, because a typo in the path must be
heard immediately, not turn into a node that runs and answers 503 forever.

**There is no fallback** — this is a deliberate price: the storage module is
mandatory on every node, including sub-nodes, which serve devices while the
control node is dead. A fleet that received `503` with `Retry-After` backs
off; a fleet that received "something built-in" would have received bytes
other than the ones verified here.

**hardened** is a launch profile, not a build profile: a node on which the
classic rollout extension is not loaded and the tenant has
`target.type.required` enabled — a target without a type gets nothing. The
profile is run by `make e2e`: before the first scenario the harness asks the
node itself for the extension inventory and configuration and refuses to work
with a node that does not match the profile. The same profile from the
protocol side is described in **API_NOTES §6** ("a device in an indeterminate
state is unacceptable"); the classic rollout falls there on the same
principle — it carries hawkBit semantics (percentages, thresholds, ignoring
the saved ordinals of conditions). Both lists describe one profile and change
in concert.

### Extension parameters

A module is given nothing ambient except the WASI environment — so
"configuring an extension" means deciding what lies in this map. The rules for
sources, format, reserved names, and secrets are in the `extension-host` spec;
here is why they are what they are.

**Two sources, the environment beats the file.** The environment is how a
deployment pins values that must match the machine: `HAWIER_EXT_FS_ROOT` must
match the volume's mount point, and no console edit should be able to break
that. The file is what the operator edits through the console without a
redeploy. The direction is the same as in systemd (`EnvironmentFile=`, then
`Environment=`) and k8s (`envFrom`, then `env`). So that this does not turn
into "editing into the void", the shadowing is made loud: a pinned row has no
edit form on the page at all, the origin is visible in every row, and a write
answers 409.

**The `KEY=value` format**, because the values **are** the guest's
environment — a flat map, and the same file already exists as the
`environment:` block in compose. A duplicate name is an error with both line
numbers, not "the last one wins": the file may hold credentials, and an
ambiguous file must not silently load on one of them. A malformed file fails
startup, a missing one does not: the mount may be late.

**Reserved names are a trust boundary, not tidiness.** The allowlist for
`http_out` is issued by the host from the **module's own manifest**, so the
choice of module is the choice of where the node may go. An operator able to
rearrange `HAWIER_EXT_STORAGE` from the console would be choosing which code
the node runs on the next load, and that code would declare itself any access
it likes. Deploying the node stays the business of whoever deploys it.

**Secrets are set but not read** — the convention of the webhook `secret` (in,
never back out), not the convention of the device token (which must be
readable so that it can be handed to a device). An empty submitted value means
"keep": an HTML input always submits something, and "empty means erase" would
wipe a key on an accidental save.

**Parameters belong to the node**, not to the tenant or the database: the
database is one for all nodes, while a sub needs its own artifact root. They
apply on restart — the module reads the environment at instantiation. In
compose the volume with the file is mounted `rw` on control and `:ro` on sub.
The inventory is served through `/rest/v1/system/extensions`, not `/ui/v1`,
because permissions classify only `/rest/v1/` paths: on the internal API the
inventory would be visible to any logged-in operator, bypassing roles.

**NARROW: a flat namespace.** The map is one for everybody, so every module
sees the parameters of all the others — `hawier-ext-fs` receives
`HAWIER_EXT_S3_SECRET_KEY` if S3 is also configured. "The node's secrets are
unavailable to the guest" is true of the *node's* secrets and untrue of a
*neighbouring module's* secrets. Excluding the reserved names narrows the gap
but does not close it; closing it is a per-section file (`[storage]`,
`[event_sink]`), and that changes what the already shipped modules receive, so
it is carried out separately.

**NARROW: the manifest can depend on a parameter.** `ext-s3` declares
`http_out` only when `HAWIER_EXT_S3_SIGNER_URL` is set, i.e. the capabilities
column is a function of a value edited in the neighbouring panel. The page
shows what was read **at startup** and says that a restart may also change
where modules are allowed to go.

## 6. Implementation order

1. **Storage + webhooks** ✅ — the first slice: proves both the contract and
   the transport, while not touching the rollout engine.
2. **cron retention** ✅ — reuses the outbox for the deletion audit.
3. **`RolloutStrategy`** ✅ — classic as an ordinary module + random-bucket.
   Touches the engine, but only via a snapshot, outside the claim
   transaction.
4. **`ConsoleSurface`** ✅ — after it, extensions get tabs for free.
5. **oauth and permissions** — permissions ✅, `AuthProvider`/OIDC — no.
6. **remote-shell** — last: the largest blast radius, under RBAC, a toggle,
   and an audit.

Verification of each slice: `make lint`, `make test`, `make it`,
`make ui-audit`, plus `make load` against `bench/load-history.csv` — the
presign cache, the outbox, and the new `_link` must not drag DDI down by more
than 20% at the same parameters.

How to maintain this file and how to add a new point — the rules are in
`openspec/config.yaml` (a point's contract goes as a delta to the
`extension-host` spec, the rationale goes here).
