# Spec Delta

## Purpose

A minimal, reproducible Linux system for QEMU x86_64 that updates itself from
hawier through SWUpdate's suricatta client. It is the real-client counterpart
of the device simulator. It follows the hardened device policy: signed images
only, exactly one hardware revision per image, A/B slots, and fallback when an
update fails to boot.

## ADDED Requirements

### Requirement: Reproducible build from a pinned tree
`make e2e-image` SHALL build the system from a Buildroot external tree kept in
the repository and from a Buildroot release pinned by version and checksum. It
SHALL use a prebuilt toolchain pinned the same way. The build SHALL run in a
build container started with the discovered container engine. The only host
requirements SHALL be the engine and make. Every output SHALL go to
`target/e2e/`, which build-cache garbage collection never touches.

The build SHALL produce:
- a raw disk image with both slots populated
- an update `.swu` for each scenario the end-to-end harness needs, built from
  the same tree

A second run with nothing changed SHALL rebuild nothing and SHALL finish
without network access.

#### Scenario: Cold build
- **WHEN** `make e2e-image` runs on a machine with a container engine and an empty `target/e2e/`
- **THEN** the disk image and the update `.swu` files exist under `target/e2e/out/`

#### Scenario: Warm build is offline
- **WHEN** `make e2e-image` runs a second time with the network unavailable and no source change
- **THEN** it succeeds and leaves the outputs untouched

### Requirement: Size and time budget
The build SHALL stay within these limits:

| Measure | Limit |
|---|---|
| root filesystem image of one slot | 8 MiB |
| each `.swu` | 8 MiB |
| raw disk image (apparent size) | 64 MiB |
| whole build tree: output, downloads, compiler cache | 4 GiB |
| cold build on a 4-vCPU hosted runner | 30 minutes |

When a size limit is exceeded, `make e2e-image` SHALL fail and name the
measure, its value and its limit.

#### Scenario: Oversized root filesystem
- **WHEN** a package added to the defconfig pushes the slot image to 9 MiB
- **THEN** `make e2e-image` fails with a message naming the slot image, 9 MiB and the 8 MiB limit

### Requirement: Read-only A/B layout
The disk SHALL carry four partitions:
- a boot partition, holding the bootloader and its environment
- root slot A
- root slot B
- a persistent data partition

Each root slot SHALL be a SquashFS image containing the kernel and the whole
root filesystem, so an update replaces both at once. The running root SHALL be
mounted read-only. Writable state SHALL live only on tmpfs and on the data
partition. The bootloader SHALL boot the slot named in its environment.

#### Scenario: Root is read-only
- **WHEN** a process on the booted device writes to `/usr`
- **THEN** the write fails with a read-only filesystem error

### Requirement: Per-boot hardware revision and identity
The hardware revision and the device identity SHALL be supplied per boot
through QEMU firmware configuration, which plays the part of a board EEPROM.
The identity consists of the server URL, tenant, controller id and target
token. The image itself SHALL carry neither. The revision SHALL be exposed in
SWUpdate's `hwrevision` format, as board `hawier-qemu` plus the supplied
revision.

A boot without a revision or without an identity SHALL NOT start the updater.
It SHALL print the missing item on the serial console.

#### Scenario: One image, two boards
- **WHEN** the same disk image is booted once with revision `rev1` and once with `rev2`
- **THEN** the device reports `hw_revision` `rev1` and `rev2` respectively

#### Scenario: Missing revision
- **WHEN** the image boots without a revision in firmware configuration
- **THEN** no update client runs, and the serial console says the hardware revision is missing

### Requirement: Device talks to hawier through suricatta
The device SHALL use SWUpdate's suricatta hawkBit client with target-token
authentication against the supplied server URL and tenant. It SHALL send
controller attributes with lowercase keys:
- `hw_revision`
- `slot`, the slot currently booted: `a` or `b`
- `version`, the image version

It SHALL install into the inactive slot only.

#### Scenario: Attributes after first poll
- **WHEN** a provisioned device boots from slot A with image version `1`
- **THEN** its target in hawier has attributes `hw_revision`, `slot=a` and `version=1`

### Requirement: Only signed images are installed
The updater SHALL verify every `.swu` against a public key built into the image.
It SHALL refuse an unsigned image or one signed with another key before
writing anything to a slot. The signing key pair SHALL be generated by the
build. The private key SHALL never be committed or copied into the image.

#### Scenario: Foreign signature
- **WHEN** the device is given a `.swu` signed with a different key
- **THEN** it reports the deployment as failed, the inactive slot is unchanged, and the next boot uses the same slot

### Requirement: Exactly one hardware revision per image
Every `.swu` produced by the build SHALL declare exactly one hardware revision
for board `hawier-qemu`, with no regular expression and no wildcard. The
updater SHALL refuse an image whose declared revision differs from the
device's revision.

#### Scenario: Wrong revision in the image
- **WHEN** a device of revision `rev1` is given a validly signed `.swu` that declares `rev2`
- **THEN** it reports the deployment as failed and the inactive slot is unchanged

### Requirement: Reboot into the new slot and confirm
After an installation succeeds, the device SHALL mark the new slot for a
trial boot and reboot. A trial boot that brings the updater up again SHALL
confirm the slot and report the deployment as successful. A trial boot that
does not reach that point SHALL be abandoned by the bootloader: the next boot
SHALL use the previous slot, and the device SHALL then report the deployment
as failed. The device SHALL never be left without a slot it will boot.

#### Scenario: Successful update
- **WHEN** a device on slot A installs a valid `.swu` with version `2`
- **THEN** it reboots into slot B, reports success, and its attributes read `slot=b` and `version=2`

#### Scenario: New slot does not boot
- **WHEN** a device installs a valid, signed, revision-correct `.swu` whose system has no init and cannot start
- **THEN** the device comes back on its previous slot and reports the deployment as failed
